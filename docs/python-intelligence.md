# Python intelligence service

Python provides segment hazard and accessibility intelligence to Go over HTTP/JSON.
Go owns routing, weather retrieval, priorities, final scores and route selection.
The service currently runs a deterministic **unvalidated heuristic baseline**. No real
hazard dataset or validated trained artifact is included.

## Run locally

Runtime requires Python 3.11+; the pinned training stack requires Python 3.12+.
Verified on Python 3.14.7 on Windows. From the repository root:

```powershell
cd backend/python
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m app.main
```

This binds to `127.0.0.1:8001`. In a second terminal, start the existing Go server
with `PYTHON_SERVICE_URL=http://localhost:8001` and `NER_DEMO_MODE=true`.
The frontend continues calling Go. This internal Python service has no public
authentication layer: keep it on loopback/a private trusted service network.

`.env.example` documents settings; `.env` is **not loaded automatically**. Export
variables in the shell. `python -m app.main` honors the configured host/port; generic
`uvicorn app.main:app` requires explicit Uvicorn host/port arguments.

| Variable | Default | Meaning |
|---|---|---|
| `PYTHON_HOST` | `127.0.0.1` | Bind address |
| `PYTHON_PORT` | `8001` | TCP port |
| `MODEL_MODE` | `heuristic` | `heuristic` or `ml` |
| `ALLOW_MODEL_FALLBACK` | `true` | Permit heuristic fallback after ML loading/inference fails |
| `LANDSLIDE_MODEL_PATH` | unset | Explicit trusted local `.joblib` path; required in ML mode |
| `FLOOD_MODEL_PATH` | unset | Optional flood artifact; otherwise flood stays heuristic |
| `MODEL_VERSION` | unset | Optional required trained-model version |
| `LOG_LEVEL` | `info` | debug/info/warning/error |
| `MAX_REQUEST_BYTES` | `1048576` | Body limit; configurable 1 KiB–10 MiB |

## API and compatibility

- `GET /health`: active engine/version, actual hazard-model readiness and startup fallback reason.
- `POST /internal/v1/risk/analyze`: validated Go-compatible request and seven response fields.
- `POST /internal/v1/risk/explain`: same request, plus per-segment contributions, summaries and limitations.

Request:

```json
{"route_id":"route-a","segments":[{"latitude":25.57,"longitude":91.88,"rainfall_mm":82,"slope_deg":34,"elevation_m":1300,"historical_landslides":7,"road_condition_score":55}]}
```

Response fields: `route_id`, `landslide_risk`, `flood_risk`, `weather_risk`,
`accessibility_score`, `confidence`, `model_mode`. All five numeric outputs are finite
and in `[0,1]`. Higher hazard values mean worse conditions; higher accessibility means better.
Shared schemas/examples are generated by `scripts/export-risk-contracts.py` and checked in tests.

The previous Go client rejected unknown JSON fields. Its only behavioral change is to
accept optional `model_mode` with values `heuristic` or `ml`; old responses without the
field remain supported. Extra explanations are kept on the separate internal endpoint.
The public Go response still reports `intelligence_mode=live` when HTTP intelligence is
available, including a Python heuristic response. **Live describes connectivity, not ML.**
Go currently replaces returned weather risk with its own weather-provider value when available;
that existing behavior is unchanged.

### Confidence definition

Go requires a numeric `confidence`. Python defines it as available required predictor values
divided by expected predictor values: five per segment. Since missing/non-finite inputs are
rejected, accepted requests return **1.0 input completeness**. This is not confidence in a
prediction, source reliability, probability of correctness or statistical uncertainty.
Do not display it as “100% confidence in route safety.” Health and explanation responses
state this meaning explicitly. Future predictive uncertainty needs a separately agreed contract.

## Design and resilience

`app/schemas.py` validates transport data; `features.py` fixes the shared feature order;
`risk/` contains rules, aggregation and engine protocol/implementations; `models/` loads
reviewed artifacts; `service.py` owns engine/fallback behavior. API handlers do no scoring.

Models load once during FastAPI lifespan, following the
[FastAPI lifecycle guidance](https://fastapi.tiangolo.com/advanced/events/).
Inference runs in a worker thread. There is no model training, dataset download or per-request
artifact reload at startup/serving. JSON logs record request ID, mode, stages and duration,
without full route bodies or exception details. Model inference should remain bounded by
the reviewed model's complexity; thread work is not forcibly killed on client cancellation.

Bodies are bounded, body reads time out after 10 seconds, and requests allow at most 1000
segments. Pydantic rejects unknown fields, strings masquerading as numbers, invalid coordinates,
NaN/Infinity, negative rainfall/history, slope outside 0–90 and road score outside 0–100.
Errors use `{ "error": { "code", "message", "request_id" } }`: 422 invalid input, 413
oversized body, 408 read timeout, 500 inference failure. Stack traces are not returned.

ML startup failure reports degraded health and heuristic mode when allowed; otherwise startup
fails. A per-request ML error or invalid ML result falls back for that request and is logged;
the explanation states why. If Python is stopped entirely, Go's own fallback remains available.

See [risk features](risk-features.md), [training](training.md), [models](ml-models.md) and
[testing](testing.md). No route index is a validated real-time hazard forecast or route clearance.
